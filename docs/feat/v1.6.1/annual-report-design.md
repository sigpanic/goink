# 年度创作报告与统计数据积累方案

状态：阶段一的每日统计、创建计数、对话/工具计数、Token 和时长采集已提交（前端时长：`c02f2af`）；writing_log 保存版本间增删量已实现，待 review，未提交；年度查询及正式报告页面尚未实现。

日期：2026-10-10。

版本目录：v1.6.1；建议本期优先完成数据记录，报告展示作为后续阶段。

设计原则：用于创作回顾和宣传，允许近似值及少量漏记、重复；优先简单实现，统计不得增加主流程的失败风险。此原则替代早期草案对逐事件去重、请求审计和事务一致性的要求。

## 1. 背景与判断

Goink 已有 writing_log 和写作活动统计，但目前不能完整回答以下问题：

- 这一年累计新增了多少字、创作了多少天？
- 创建过多少本小说、多少章、多少个人物、多少个地点？
- 大约投入了多少创作时间，与 AI 对话了多少轮、调用了多少次工具？
- 使用了多少输入、输出 Token，最常使用哪个模型？
- 哪部作品投入最多，哪个月份创作最活跃？

建议现在开始积累必要数据，后续再实现年度报告。报告页面可以晚些开发，未记录的历史请求用量和已删除实体的创建历史很难可靠补回。

这项功能的技术难度中等偏低，没有复杂算法。主要工作是接入常用操作入口和汇总展示；异常边界允许偏差，不为统计新增补偿、恢复或可靠投递机制。它适合在核心写作流程稳定后安排，不应挤占保存可靠性、AI 调用稳定性等基础功能的修复时间。

产品价值主要来自创作积累的反馈。报告应优先呈现作品、人物、地点、字数和创作习惯，Token 用量作为辅助信息。是否能提升留存或分享意愿，需要上线后验证。

## 2. 当前代码基础

| 能力 | 现状 | 对年度报告的影响 |
|---|---|---|
| 写作日志 | `internal/writing/types.go` 的 WritingLog 保留净变化，补充保存版本间的新增、删除量 | 在已有表增加两列，无需新建字数日志表 |
| 写作统计 | `internal/writing/store.go` 按新增量汇总，历史记录回退到正向 delta，计算活跃天数和连续天数 | 仍需增加固定年度范围查询，不能直接使用全局统计或滚动 12 个月替代 |
| 字数记录入口 | `app/content.go` 和 `internal/mcp_tools/rw_tools.go` 共用后端 diff | 保存成功后记录正文增删，等长改写也可以累计新增量 |
| 实体创建时间 | Novel、Character、Location 均有 CreatedAt | 只能查询仍然存在的实体，不能表示期间曾经创建过的总数 |
| 会话用量 | `internal/session/store.go` 的 UpdateSessionUsage 覆盖最近一次用量 | 不能从 Session.Usage 还原全年累计用量 |
| 缓存用量 | `internal/agent/tokens.go` 对部分缓存字段做会话累计 | 与最近一次输入、输出用量的口径不同，不能直接整体累加 |
| 模型请求 | Agent 使用 ChatStream；模式提取、风格提取等也使用 CallTool | 优先接入主对话，辅助调用在容易接入时补充，不要求全量覆盖 |
| 章节创建 | `internal/chapter/service.go` 已有章节创建能力 | 在现有成功返回位置累计章节数 |
| 对话和工具 | Agent 已有对话执行、工具执行与状态事件 | 在用户请求被接受和工具开始执行时分别累计 |
| 创作时长 | 前端能够感知窗口可见性、焦点与交互 | 使用低频心跳估算前台活跃时间 |
| 操作日志 | operation_log 用于 AI 操作回退，会随会话删除而清理 | 不适合作为长期创作统计的数据来源 |

当前小说创建先写数据库，再初始化小说 Git 仓库；初始化失败时会删除数据库记录。选择现有完整流程的成功返回位置计数即可，不为统计重构小说创建流程。

## 3. 分阶段范围

### 阶段一：从启用之日起记录数据

1. 保存一次性的统计起始时间。
2. 按天累计小说、章节、人物、地点创建数，覆盖常用手动操作和 AI 工具。
3. 按天累计对话轮数、工具执行次数。
4. 用前端低频心跳估算创作时长。
5. 累计能方便取得的单次 Token 用量，保存模型和用途维度。
6. 复用 writing_log，验证正常路径、并发累加和统计失败不影响主流程。

阶段一不依赖用户打开报告页面，计数与持久化在后端执行，时长由前端提供近似活动时间。数据保存在现有本地数据库，随数据目录一起迁移或备份。

本阶段暂不包含历史回填、费用估算、手写与 AI 字数归因、远程统计服务、分享动画及图片导出。也不包含事件唯一键、逐请求审计、持久化重试队列、崩溃补记或统计与业务的强事务绑定。

### 阶段二：年度汇总与基础页面

1. 按指定自然年查询统计结果，支持全局汇总，预留按小说查询能力。
2. 展示创作成果、活动分布和 AI 使用情况。
3. 说明统计开始日期、实际覆盖时间，以及创作时长和用量属于近似统计。
4. 数据不足时展示真实的简短回顾，避免空排行榜或夸大的结论。

### 阶段三：展示扩展

按实际需求增加分享卡片、图片导出、月度回顾和视觉效果。基础统计同样可以用于月报，不必等到年底才能提供反馈。

## 4. 统计口径

### 4.1 时间范围

- 年度表示当地自然年的 1 月 1 日至下一年 1 月 1 日，采用左闭右开范围。
- 新统计的起点为首次成功启用记录的时间，不是文档日期或版本发布日期；重复启动、升级不得重置。
- 按后端记录时的本地日期归入当天，与 writing_log 一致。跨日调用归入记录到达的日期，用户切换时区后不重新归属已有数据。
- 首年仅统计启用后的实际覆盖区间。报告明确写出“自 YYYY-MM-DD 开始记录”，不宣称覆盖整年。
- writing_log 已有历史继续保留；首版统一报告使用启用后的范围。将来若展示更早的字数历史，应单独标注其覆盖范围。
- 月报和年报复用同一范围查询能力，避免分别实现计数规则。

### 4.2 字数与写作活动

累计新增字数为保存版本间 diff 得到的新增量之和；写作活跃日为存在新增或删除量的日期。每日查询同时返回 `words_added`（新增）、`words_deleted`（删除）、`words`（净增，直接汇总 `word_delta`），净增允许为负数。

旧记录没有 diff 信息，新增量使用 `max(word_delta, 0)`，删除量使用 `max(-word_delta, 0)`，仅是按净变化估算，无法还原一次保存内同时发生的增删。新记录优先使用增删字段，NULL 时才回退；不回填数据库历史列。

采用 `github.com/sergi/go-diff/diffmatchpatch` 比较计数单位序列：中文按汉字、英文按完整单词，复用现有英文分词规则，忽略标点、空白和数字。设置 100ms 的 diff 搜索预算，复杂文本允许使用近似结果；这不是整个保存流程的硬耗时上限。

正常保存直接复用已通过冲突校验的 `ExpectedContent`；没有旧版本参数时沿用原有直接写入，跳过该次增删统计，不额外读取磁盘旧正文。当前正常前端保存入口均提供旧版本参数。AI 工具复用本次编辑读取的旧正文与最终正文，只有成功完成写入和必要的元数据更新后记录。数据库中的章节 `word_count` 仍只表示当前存量，不作为 diff 的旧版本。

- 原来 800 字，删除 200 字、新增 250 字后一次保存：记录新增 250、删除 200、净变化 50；相同文字的匹配可能影响增删分配。
- 等长改写记录增删量，净变化可以为 0；英文单词的部分字母修改按一个旧单词被一个新单词替换计数。
- 纯删除保留删除量，不增加累计新增字数，但计入写作活跃日；没有增删计数单位时不写日志。
- 增加 100 字、保存、删除、保存、再加回并保存，会累计新增 200 字。两次保存之间输入又删掉的内容无法观察。
- 前端现有自动保存是停止编辑约 500ms 后触发的防抖，不是每 500ms 固定保存；持续输入过程不逐次计数。
- 移动段落、重复文字和撤销恢复可能被解释成增删，不能用该值表示逐键输入量或精确修改工作量。
- 粘贴和 AI 写入均可计入，不区分作者来源；历史增删量无法还原，不回填成精确数据。

页面使用“累计新增字数”等准确文案。当前作品字数属于另一项存量指标，不能用当前存量推导年度新增量。

现有个人页写作日历按“新增＋删除”的编辑量着色，提示同时展示新增、删除、净增（正值带加号，负值保留负号）。等长改写和纯删稿也能显示活跃；编辑量用于反映活动，不表示净增长。累计卡片使用“累计新增字数”文案。

连续写作天数按有增删的日历日期计算，年度最长连续天数裁剪到报告覆盖区间。最活跃月份可按编辑量汇总；单日最高新增字数和作品新增字数排名使用新增量口径；范围内包含旧记录时，说明旧增删量采用净变化估算。

### 4.3 小说、章节、人物、地点

“创建数量”表示在已接入的创建入口成功返回后累计的数量，后续删除实体、删除小说或删除会话不减少该历史累计值。空章节创建也计数。

| 场景 | 首版规则 |
|---|---|
| 手动创建成功 | 记录一次 |
| AI 工具创建成功 | 记录一次 |
| 创建入口返回失败 | 不主动计数；复杂内部补偿造成的偏差可接受 |
| 小说 Git 初始化失败并补偿删除 | 不记录成功创建 |
| 少量异常重复或漏记 | 接受；正常路径只调用一次计数，不增加专门去重机制 |
| 真正执行两次创建且都成功 | 记录两次，不按名字合并 |
| 重命名或普通更新 | 不增加创建计数 |
| 删除成功创建过的实体 | 保留原累计数 |
| AI 操作回退，撤销已成功创建的实体 | 不扣减累计数；报告明确是历史创建次数 |
| 回退恢复旧实体 | 不计为新的创作 |
| 导入、复制 | 复制若走正常创建入口就计数；批量导入不专门补记，不要求新增来源分类 |

在正常创建入口显式计数即可，恢复路径不专门接入。统计不追溯回退，也不通过扫描当前实体校正历史计数。

已接入的入口：App 的 `CreateNovel`、`CreateChapter`、`PlaceChapter` 新建分支、`CreateCharacter`、`CreateLocation`，以及 MCP 的 `create_character`、`create_location` 和 `edit` 新建章节通道。批量角色、地点在业务事务成功后按实际条数累加；章节需完成文件写入，移动不增加计数。`outlines/new.md` 同样会创建章节记录，因此累计一次，随后为该记录补写正文不重复累计。统计独立写入每日表，失败只告警，不新增业务补偿或可靠投递机制。

### 4.4 创作时长

创作时长定义为“在 Goink 创作工作区内的近似前台活跃时间”，包含写正文、阅读修改、整理设定和与 AI 交互。它不是精确的键盘输入时间。

- 前端仅挂载一个活动统计 hook，避免多个编辑器、标签页重复计时。
- 窗口可见且具有焦点，并且最近 5 分钟有键盘或指针交互时视为活跃。
- 前端先累计活跃毫秒，每 60 秒统一上报，单次最多计 60 秒。隐藏或失焦前保留已发生的尾段，闲置只累计到最后一次交互后的 5 分钟边界；恢复时不补回暂停时间。
- 使用简单的交互时间戳和定时器，不新增精确的操作轨迹或跨会话状态机。
- 正常退出不强求补记不足一分钟的尾段；强制退出、睡眠、系统计时变化等造成的偏差可接受。
- 前端不支持可靠焦点检测时，允许退化为可见性加交互判断。页面展示“大约投入 X 小时创作”。

60 秒间隔和 5 分钟闲置阈值作为初版默认值，不新增用户设置项。

后端已提供 `RecordCreativeActivity(seconds int64)`，直接调用现有 activity Store 累计当天的 `creative_seconds`，不新增表。非正数忽略，超过 60 秒截为 60 秒；Store 未就绪时跳过，写入失败只告警，接口不返回统计错误。Wails 绑定通过 `wails generate module -tags webkit2_41` 生成。不增加去重、重试或跨日拆分。

前端已在 `WorkspaceView` 根层挂载一个 `views/workspace/useCreativeActivity`，不按小说或编辑器重复挂载；初始化和加载页面不计时。用捕获阶段的 `keydown`、`pointerdown`、`pointermove` 和 `wheel` 更新时间戳，首次交互后才开始累计。交互、焦点/可见性变化和心跳时先结算上一次采样以来的活跃区间，毫秒累计在内存中，隐藏或失焦前的尾段不会丢失；已累计的秒数也可在后台心跳上报。闲置区间截到最后交互后的 5 分钟边界，恢复时只计新的前台活跃时间。统一每分钟上报，保留不足一秒的余数，不因窗口切换增加数据库写入频率。两次采样间隔达到 5 分钟视为长时间暂停并跳过该间隔；单段累计和单次上报最多 60 秒，超出上报上限的部分丢弃，不跨分钟补发。缺少 `document.hasFocus` 时退化为可见性和可取得的焦点事件判断。接口失败跳过，不补发；卸载清理全部监听和定时器，不补记退出尾段，StrictMode 重挂载不会留下多个计时器。

### 4.5 对话轮数

用户发起的一次对话请求被后端接受并开始处理时累计 1 轮。一次用户请求内的多次模型调用、工具循环和内部重试不额外增加轮数。

用户主动重新生成或重试按一次新请求计数；已开始后报错或取消仍计入。单独执行模式、风格提取等辅助功能不计为对话轮数。

直接在现有对话启动入口累计，不从消息表反推，不为请求新增去重 ID。

已接入 `App.Chat`：本轮用户消息事务成功后累计一次，统计写入位于事务外。模型不存在、消息保存失败等接受前的失败不计入；接受后加载上下文、模型调用或取消导致的失败不扣减。用户再次提交请求再次计数，自动标题、压缩和子 Agent 不经过该入口，不增加对话轮数。

### 4.6 工具调用次数

每次通过 Registry 实际开始执行一个 Goink 工具时累计 1 次，内部 Agent 和外部 MCP 调用统一计入，成功、失败均计入，实际重新执行也计入。并行执行多个工具按各工具分别累计。

接在工具执行位置，不在多个开始、完成或状态事件中重复计数；仅生成了调用参数、被取消或拦截而未执行的不主动计数。

首版统计 Goink 工具执行总次数，不要求逐工具排行榜，也不区分内部 Agent 和外部 MCP 来源。

已直接接入 `Registry.Execute`：名称、白名单和参数校验通过后、进入 `Tool.Execute` 前累计，使用现有 `ToolContext.DB` 和 logger，不需要回调、来源标记或 Agent 包装。不存在、禁止使用、参数不合法，以及中断时直接跳过的待执行工具不计入。进入工具后发生业务失败、系统错误、panic、审批拒绝或取消仍保留次数；这是执行尝试数，不是成功修改数据的次数。MCP 协议内置的 `get_current_novel` 未经过 Registry，不计入；无数据库的测试上下文跳过记录。统计沿用当前请求上下文，取消恰好发生在写入前等情况允许漏记，不补写。

### 4.7 Token 用量

- 在取得单次请求最终 usage 的现有位置累计。同一轮对话取得多次 usage 时分别累加；对话轮数与模型请求次数是不同指标。
- 输入和输出取服务商返回的单次请求用量，不取 Session.Usage 中经过会话累计的值。
- 总用量优先采用服务商返回的 total；缺失时，在输入和输出都已知时计算。未返回的字段跳过，不估算缺失消耗。
- 缓存命中、未命中以及推理用量作为明细保存，按服务商语义解释，不再次叠加到 total。
- 每个请求只累加一次最终 usage，不逐个 SSE chunk 累加；已有流式处理对 lastUsage 的缓冲可以复用。
- 没有取得 usage 就跳过；中断、报错或写入失败造成的漏记可接受，不额外保存请求结果和缺失请求明细。
- 报告展示“已记录 Token 用量”，不宣称等于账单或实际全部消耗。
- 记录 provider、实际请求模型和用途，避免用户修改模型配置后历史被重新归属。
- 首版优先覆盖主对话；模式、风格提取等辅助调用能通过小改动接入时补充。不能为了取得这些用量重写调用生命周期。本地 ONNX 推理不计 API Token，远程 embedding 留待后续。

已在 `agent.updateUsage` 的起点调用 `recordTokenUsage`，复用现有 SSE 最终 usage 事件。记录 `prompt_tokens`、`completion_tokens`、`total_tokens`，以及 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 明细；缓存命中字段未返回时读取 `prompt_tokens_details.cached_tokens`，推理明细读取 `completion_tokens_details.reasoning_tokens`。至少取得一个已知用量字段才记录，全零但明确返回的用量也计入 usage_count。主 Agent 用途为 `chat`，共用此路径的子 Agent 按其 AgentType（如 `review`、`memory`）保存用途；自动标题、压缩、模式/风格提取等辅助路径尚未接入。转换使用现有 JSON 解码的数值类型，不修改原始 usage，也不读取会话累计值；数据库失败仍只告警。

## 5. 建议的数据设计

以下表名与字段为设计建议，实际实现前需结合现有迁移和调用边界确认。

采用按天累计的简单计数表，代替早期草案的 creation_events 和 llm_usage_records 明细表。年报、月报通过日期范围求和，不需要保存每一次操作。

### 5.1 统计元信息

复用现有 `app_config` 单行配置，增加 `tracking_started_at`（可空 UTC 时间）和 `tracking_start_date`（起始本地日期），不新增元信息表。应用初始化时在迁移之后、加载运行时设置之前条件写入一次，已有起点不覆盖。先初始化再加载设置，避免后续保存设置时写回未初始化的旧值。备份恢复沿用原起点，不以应用重启时间覆盖。

这两个字段属于内部统计元信息，当前通过 `json:"-"` 排除在已有设置 API 的序列化结果之外，年度报告 API 实现时再提供覆盖区间。

### 5.2 每日活动表：activity_daily

| 字段 | 用途 |
|---|---|
| date | 本地日期，主键；每日一行全局统计 |
| novels_created / chapters_created | 当天创建的小说数、章节数 |
| characters_created / locations_created | 当天创建的人物数、地点数 |
| creative_seconds | 当天累计的近似创作秒数 |
| conversation_turns | 当天累计的用户对话轮数 |
| tool_calls | 当天累计的工具执行次数 |

使用数据库原子的 `INSERT ... ON CONFLICT DO UPDATE` 增量累加，避免并发时读旧值再写回造成计数覆盖。这是基本累加正确性，不增加事件去重或业务事务。

创建数、时长和对话等新增指标首版按全局统计，不新增小说、实体、会话的关联，也不设置删除级联。作品字数排名继续使用 writing_log 的 novel_id；已删除作品显示为“已删除作品”。

### 5.3 每日模型用量表：llm_usage_daily

| 字段 | 用途 |
|---|---|
| date / provider / model / purpose | 日期、服务商、模型、用途，组成唯一键 |
| usage_count | 取得并累计 usage 的次数；不等于全部实际请求次数 |
| input_tokens / output_tokens / total_tokens | 对已取得字段的累加，使用 64 位整数 |
| cache_hit_tokens / cache_miss_tokens / reasoning_tokens | 已取得的用量明细累加；无值时跳过 |

同样通过原子增量累加，不保存 request_id、session_id、turn_id、请求状态或完整 usage JSON。缺失字段不贡献累加值；页面不把累计值为 0 解释为服务商明确返回了零用量。

数据量按日期和模型维度增长，不随每次操作或流式 chunk 增长。首版不保存人物设定、章节正文、提示词或 API 密钥，不引入额外统计数据库或后台聚合服务。

### 5.4 现有写作日志：writing_log

不新增字数表，在现有日志上增加两列：

| 字段 | 用途 |
|---|---|
| date / novel_id / chapter_id | 保留现有日期和作品、章节关联 |
| word_delta | 保留净变化，即新记录的新增量减删除量 |
| words_added / words_deleted | 可空整数；新记录保存 diff 增删量，旧记录保持 NULL |
| id / created_at | 沿用现有日志主键和保存时间 |

通过现有 AutoMigrate 添加字段，不回填历史增删量，也不保存正文或完整 diff。等长替换保留日志，标点或空白变化不单独写入。

## 6. 接入与分层

### 6.1 轻量统计 Store

建议由 `internal/activity/` 等小型统计包管理元信息、按天累加和汇总，包名在实现时确定。它只负责本地数据库读写，不创建空壳 Service。

- 计数方法失败时记录告警并返回，不向业务流程传播错误。
- 使用正常的数据库增量更新，不新增队列、后台恢复、锁服务或可靠投递框架。
- 在已有成功返回或执行位置加一次调用；公共入口能直接复用时复用，分散入口用少量显式调用也可以。
- 不为了统计调整业务事务、重构小说 Service、改变 Git 补偿流程或修复既有 writing_log 一致性。
- 仅接常用创建入口，不注册所有数据库插入的通用回调，不复用 operation_log 作为计数来源。

### 6.2 对话、工具与时长

- 对话：在后端接受用户请求、开始处理的入口累计一次。
- 工具：在 Registry 通过校验、开始实际执行工具的位置累计一次，内部 Agent 和外部 MCP 统一计入，避免开始和完成事件各计一次。
- 时长：前端根层活动 hook 每分钟向轻量 App API 提供本次秒数，后端限定单次不超过 60 秒并归入当天。失败跳过，不补发或重试。
- 活动 hook 清理监听和定时器，避免组件重复挂载导致持续重复累计。

### 6.3 Token 用量路径

优先在 `agent.updateUsage` 取得原始 apiUsage 的位置累计，使用单次原始字段，避免取经过会话累计的缓存字段。

辅助调用如需接入，在已有用量回调或小型 observer 接口中注入统计能力；LLM 层不直接依赖 Wails 或具体数据库 Store。同一调用只选一个统计位置。

CallTool 提前返回、取消或错误可能导致最终 usage 没有到达统计入口，这类漏记允许保留。现有传输流程继续运行，统计功能不要求重写收尾逻辑，也不增加取消后的补写上下文和持久化重试。

### 6.4 回退、删除与失败

每日统计属于独立累计，不进入 AI 业务操作回退的目标集合，也不参与实体或会话清理。若写入路径携带 TurnInfo，将新表排除在 operation_log 自动记录之外即可，不改回退算法。

写入失败、异常退出、少量重复通知和边界时间误差均允许造成偏差。正常入口接对一次即可，不追求 exactly-once，不为统计故障中断用户创作。

报告查询失败显示获取失败，避免把错误展示成整年没有创作。页面统一用简短的“数据为近似统计，自某日开始记录”说明，无需逐项审计报告。

## 7. 报告内容草案

建议按下列顺序展示：

1. **创作成果**：创建的小说、章节、人物、地点，以及累计新增字数。
2. **创作习惯**：近似创作时长、写作活跃天数、最长连续写作、活动热力图、最活跃月份。
3. **作品投入**：按累计新增字数展示投入最多的作品。
4. **AI 使用**：对话轮数、工具调用次数、已记录输入与输出 Token、模型分布。

示例文案：

> 自开始记录以来，你开启了 3 个故事，创造了 86 位人物和 24 个地点。
> 你创建了 120 个章节，大约投入 260 小时创作。
> 有 127 天留下了新增文字，和 AI 对话了 860 轮，执行了 3,200 次工具调用。

首版可使用固定模板生成文案，数据汇总结果是唯一事实来源。若以后加入 LLM 润色，不允许模型自行推算或编造统计数字。

## 8. 实现文件范围与提交路线

本节为预计路线，实施前需再次核对入口并确认方案。各提交仅作为拆分建议，完成代码后先等待 review，Git 写操作另行授权。

逐个提交的范围、顺序、验证要求与进度以配套 [Commit 路线](./commit-roadmap.md) 为准。本节保留文件范围概要。

| 步骤 | 预计范围 | 目的 |
|---|---|---|
| 1. 数据基础 | `internal/activity/`（拟新增）、`internal/migrate/`、`internal/storage/` 排除名单、初始化注入位置 | 起始时间、每日累计表、原子增量更新 |
| 2. 计数接入 | 已有 `app/`、`internal/chapter/`、`internal/mcp_tools/` 创建入口及 `internal/agent/` | 创建数、对话轮数、工具次数与主对话 Token |

建议按“数据基础 → 计数与 Token 接入 → 时长估算 → 报告展示”拆分。每阶段完成后验证并等待 review；自动生成的 Wails 绑定通过生成命令更新，不手工编辑。

## 9. 验证方案

重点验证正常使用及统计不影响主流程，无需穷举所有异常情况。

### 后端验证

- 起始时间只写入一次，升级、重启和重复初始化不改变原值。
- 常用手动和 AI 创建入口、对话入口、工具执行入口正常累计，普通更新不增加创建数。
- 并发累加不覆盖旧值，按天和按年求和结果正确。
- 统计写入失败不改变创建、对话、工具执行的返回结果。
- 删除实体、小说或会话后，每日统计仍在。
- 新表写入不产生可回退的 operation_log 条目。
- 原始单次 usage 正常累加，不将会话累计缓存字段或逐 chunk 用量重复加入。
- writing_log 验证等长替换、一次保存同时增删、中英文计数、冲突不记录、旧记录兼容，以及统计失败不阻塞正文保存。

### 前端与手动验证

- 前台交互时累计时间；后台、失焦、长时间闲置时停止累计。
- 组件重新挂载后不留下重复定时器或监听，暂停恢复不补记长间隔。
- 一次用户请求中执行多个工具，轮数计一次、工具按执行次数计数。
- 空数据与查询失败可区分，报告展示统计起点与近似说明。
- 检查年度日期范围和连续天数；接受分钟级尾段、跨日归属和异常退出误差。

Go 构建与测试从仓库根目录执行 `go build ./...`、`go test ./...`；按变更范围补充原子累加和失败隔离等有意义的测试。前端时长或报告实现后，在 `frontend/` 执行 build、lint、test，并手动检查活动计时与空数据展示。

## 10. 工作量与优先级

以下为基于当前代码检查的粗估，包含验证和 review 修正，不是排期承诺：

| 工作项 | 预计开发时间 |
|---|---|
| 统计口径、每日累计表和迁移 | 0.5～1 天 |
| 创建数、对话轮数、工具次数与主对话 Token 接入 | 1～2 天 |
| 前台活跃时长估算 | 0.5～1 天 |
| 正常路径验证与修正 | 0.5～1 天 |
| 年度汇总与基础报告页面 | 2～3 天 |
| 分享卡片、导出与视觉打磨 | 1～2 天 |

简化后的阶段一暂按约 3～5 个开发日预留，包含新增的四项指标；完整报告连同展示扩展约 6～10 个开发日。估算待实际接入检查后调整，辅助用量若需要较大改动则后置，不因此扩大首版。

推荐近期安排阶段一，让数据尽早开始积累。基础记录验收后再根据核心功能进度决定报告页面的排期。

## 11. 已确定的取舍

1. 增加章节创建数、近似创作时长、对话轮数、工具调用次数。
2. 接受偏差，以简单的按天累计为主；不要求审计或账单级准确。
3. 统计失败不影响主流程，不为统计引入重构、强事务、去重框架或恢复机制。
4. 使用本方案中的简单默认口径，细小边界不再作为实现前的逐项确认条件。

存储基础已按 Commit 路线第 2 项实现，其余步骤按路线继续；每阶段验证完成后等待 review，再由用户授权提交。
