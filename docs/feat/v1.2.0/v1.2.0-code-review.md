## 二、严重问题（必须修复）

### 2.1 loadAPIMessages 跨 turn tool_call_id 去重漏洞

- **位置**：[app/chat.go:274-322](file:///home/nianhe/projects/todo/app/chat.go)
- **描述**：`validToolCallIDs` 与 `seenToolMsgIDs` 跨整个消息列表累积，未按 turn 重置。当 LLM 跨 turn 复用同一 `tool_call_id`（DeepSeek 长会话曾出现）时，第二轮的 tool 消息会被误判为"重复"而跳过。
- **影响**：`assistant.tool_calls` 与 tool 消息不匹配，反而触发该函数本想规避的 DeepSeek 400 错误。当前 `TestLoadAPIMessages_MultipleTurns` 只用不同 ID，未覆盖此场景。
- **建议**：`seenToolMsgIDs` 在每条 assistant 消息处理完毕后清空，或改为"同一 assistant 消息内的 tool_calls 与紧随其后的 tool 消息匹配"的局部窗口语义；补充跨 turn 复用 ID 的测试用例。

### 2.2 SlashMenu 与 ChatInput 过滤列表不一致导致选中错项

- **位置**：[frontend/src/components/chat/SlashMenu.tsx:70-72](file:///home/nianhe/projects/todo/frontend/src/components/chat/SlashMenu.tsx) + [frontend/src/components/chat/ChatInput.tsx:38-42](file:///home/nianhe/projects/todo/frontend/src/components/chat/ChatInput.tsx)
- **描述**：ChatInput 用简单 `includes` 过滤并保持原始顺序传给 SlashMenu，而 SlashMenu 内部又用 `score()` 评分模糊匹配并按分数排序。两份列表项顺序不同时，`selectedIndex` 从 ChatInput 来但索引的是 SlashMenu 排序后的列表。
- **影响**：用户看到高亮的是 `filtered[0]`，按 Enter 实际选中 `filteredItems[0]`（不同项）。例如 slashItems 含 `xab` 和 `abc`，输入 `/ab` 时高亮 `abc` 但 Enter 选中 `xab`。
- **建议**：移除 SlashMenu 内部重复过滤/排序，或让 ChatInput 也用相同的 score 排序后传给 SlashMenu，确保两份列表顺序一致。

## 三、警告问题（建议修复）

### 3.1 后端 AI 核心

#### 3.1.1 tool_args_invalid 重试残留孤立 reminder

- **位置**：[internal/agent/agent.go:368-403](file:///home/nianhe/projects/todo/internal/agent/agent.go)
- **描述**：`tool_args_invalid` 重试路径每次都 `appendMsg("user", reminder, ...)`，但失败的 assistant 消息被丢弃不入库。若 5 次重试均失败或用户在退避期间取消，DB 中会残留最多 5 条孤立 user reminder，且没有对应 assistant 上下文。
- **影响**：下一轮 LLM 会看到"你刚才尝试了工具调用但是解析错误"却不知道自己调用了什么，可能导致重复犯错或对话混乱。连续多条 user 消息非 OpenAI 标准交替模式，其他 provider 可能拒绝。
- **建议**：重试失败或 ctx 取消时回滚/删除本轮新追加的 reminder；或改为保留失败 assistant 消息（标记 ToAPI=false 仅前端可见）+ reminder 配对。

#### 3.1.2 重试退避 time.After 未停止

- **位置**：[internal/agent/agent.go:445-452](file:///home/nianhe/projects/todo/internal/agent/agent.go)
- **描述**：重试退避用 `time.After(backoff)`，最长 120s。用户在退避期间取消时 `time.After` 未被停止，运行时会保留定时器直至触发。
- **影响**：单次影响有限，但长会话中多次重试取消会累积定时器。
- **建议**：改用 `t := time.NewTimer(backoff); defer t.Stop()` 配合 select。

#### 3.1.3 RunSubAgent 丢失 error 链

- **位置**：[internal/agent/agent.go:128](file:///home/nianhe/projects/todo/internal/agent/agent.go)
- **描述**：`RunSubAgent` 用 `fmt.Errorf("%s", FriendlyError(err))` 把错误转为字符串，丢失原始 error 链。
- **影响**：父 agent 的 `run_subagent` 工具拿到的是友好化字符串，无法用 `errors.Is`/`errors.As` 区分错误类型（如 401 vs 429）。
- **建议**：若需保留错误类型可用 `fmt.Errorf("%w", err)` 包装；若有意只传友好文案，可加注释说明。

#### 3.1.4 网络错误盲目重试

- **位置**：[internal/llm/stream.go:120-141](file:///home/nianhe/projects/todo/internal/llm/stream.go)
- **描述**：网络错误一律标记 `Retryable: true`，包括 DNS 解析失败、连接拒绝等不可恢复错误。agent 会盲目重试 5 次（累计 ~41s）。
- **影响**：浪费时间且对用户无益。
- **建议**：结合 `errors.Is(err, net.ErrTemporary)` 或 DNS 错误类型做更细粒度判断；至少对 `*net.DNSError` 且 `IsNotFound` 的情况标记为不可重试。

#### 3.1.5 parseSSE 双 EventError

- **位置**：[internal/llm/stream.go:388-444](file:///home/nianhe/projects/todo/internal/llm/stream.go)
- **描述**：`parseSSE` 在 `scanner.Err()` 触发后仍会继续执行"流结束后"逻辑，可能再发一个 `tool_args_invalid` 或"流式响应为空"的 EventError。
- **影响**：一条流产生两个 EventError，agent 只处理第一个，第二个被静默丢弃；同时 `scanner.Err()` 错误重置了 buffer 但 tool args 检查又访问了被中断的 accumulated，状态不一致。
- **建议**：`scanner.Err()` 后直接 return，不再做 tool_call 收尾检查。

### 3.2 后端业务/工具

#### 3.2.1 InstallRemoteSkill 路径校验缺失

- **位置**：[internal/skill/remote/service.go:180](file:///home/nianhe/projects/todo/internal/skill/remote/service.go)
- **描述**：`InstallRemoteSkill` 中 `name` 未经校验直接用于 `filepath.Join(dir, name+".md")` 构造本地写入路径。与 `app/skill_api.go` 的 `DeleteSkill`（使用 `git.SafePath` + `filepath.Base` 严格校验）形成鲜明对比。
- **影响**：若 `name` 含 `../`，`filepath.Join` 清理后可逃出 skills 目录。虽然远程 GitHub fetch 对穿越路径大概率 404，但若远程 index.json 被污染或仓库存有可穿越命中的文件，本地写入会落到 skills 目录之外（如 `~/.goink/goink.md` 覆盖故事状态）。
- **建议**：在 `InstallRemoteSkill` 和 `GetRemoteSkillContent` 入口对 `name` 做 `filepath.Base(name)` 取纯文件名，或复用 `git.SafePath(dir, name+".md")` 做路径包含校验，与 `DeleteSkill` 保持一致。

#### 3.2.2 update 工具 RawArgs→Save 不可变字段覆盖

- **位置**：[internal/mcp_tools/timeline_tools.go:244](file:///home/nianhe/projects/todo/internal/mcp_tools/timeline_tools.go) / [character_tools.go:259](file:///home/nianhe/projects/todo/internal/mcp_tools/character_tools.go) / [location_tools.go:359](file:///home/nianhe/projects/todo/internal/mcp_tools/location_tools.go) / [storyarc_tools.go:258,397](file:///home/nianhe/projects/todo/internal/mcp_tools/storyarc_tools.go) / [reader_perspective_tools.go:258](file:///home/nianhe/projects/todo/internal/mcp_tools/reader_perspective_tools.go)
- **描述**：多个 update 工具采用 `json.Unmarshal(tc.RawArgs, &entity)` + `db.Save(&entity)` 模式实现 PATCH 语义。`RawArgs` 是 LLM 原始 JSON（不经字段过滤），若 LLM 回传完整实体（含 `id`、`novel_id`、`source_chapter`、`category`、`created_at` 等非 schema 字段），这些字段会被 Unmarshal 覆盖查询值后被 `Save` 全字段写入。
- **影响**：(1) `id` 被覆盖 → `Save` 更新到另一行（跨行/跨小说数据污染）；(2) 文档标注"创建后不可变"的 `source_chapter`/`category` 实际可被篡改；(3) `created_at` 审计时间被改写。
- **建议**：改用 `db.Updates(map)` 仅写入 Args 中声明的可变字段，或在 Unmarshal 后从查询结果回填 `ID`/`NovelID`/`CreatedAt`/不可变字段。

#### 3.2.3 CodeFromError 字符串匹配脆弱

- **位置**：[internal/apperr/apperr.go:127-129](file:///home/nianhe/projects/todo/internal/apperr/apperr.go)
- **描述**：`CodeFromError` 的 fallback 用 `strings.Contains(msg, "invalid")` 字符串匹配来分类 `CodeInvalid`。
- **影响**：任何模块的错误消息含 "invalid" 一词（如 OS 层 "invalid argument"、GORM "invalid connection"）都会被误判为入参错误。错误码字符串值已是前端契约（apperr_test.go:154 有稳定性测试），后续扩展模块时隐患会放大。
- **建议**：为业务校验错误定义哨兵错误（如 `var ErrInvalidTarget = errors.New(...)`）或自定义错误类型，用 `errors.Is`/`errors.As` 替代字符串匹配。

## 五、总体评价

3 个领域整体设计合理、测试覆盖较好。重试机制、tool_call 去重、首字节超时、Kimi K3 适配、子 agent 事件路由、远程技能市场、错误码系统等核心改动设计清晰。

**优先修复建议**：

1. **2 个严重项**：tool_call_id 跨 turn 去重漏洞（可能导致 DeepSeek 400）、SlashMenu 选中错项（用户可感知的 UX bug）
2. **高优先警告**：update 工具 RawArgs→Save 安全缺口（数据污染风险）、InstallRemoteSkill 路径校验缺失（与 DeleteSkill 不一致）、pre-commit 空格拆词（我刚写的 hook 问题）

其余警告和提示项可作为后续迭代的技术债务清单逐步消化。
