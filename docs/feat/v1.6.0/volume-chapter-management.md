# 卷与章节一体化管理

> 本文档描述 v1.6.0 在已有稳定章节 ID 与分卷数据模型之上，新增的用户可见结构管理能力；不描述具体代码实现。

## 目标

将卷管理与章节管理放在同一个独立的“章节管理”Tab 中。卷是章节的分组和阅读顺序的一部分，用户应能在同一界面完成建卷、调卷、建章、插章、移动和删除章节；不再拆成两个入口或两个 Tab。

现有 SidePanel 的 `ChapterList` 保持为写作时的快速切章入口，不承担结构管理职责。

写作侧栏按卷顺序展示可折叠的卷与末尾的“未分卷”组，故事状态仍独立置顶。卷内章节保持阅读顺序；超过 100 章时用紧凑的区间选择器只展示当前区间，区间标题使用全书实时章节号，不跨卷拼接。当前打开的章节所在卷和区间应自动可见；切换小说时不沿用上一部小说的展开与区间选择。没有卷时仍可在未分卷组浏览和新建章节。卷纲入口留在对应卷内的章节列表之前，随前端卷纲读写单独接入。

侧栏顶部、各分组与章节管理页的新增章节入口共用创建弹窗及表单，明确标题与目标卷；组内入口预选该组，顶部入口预选当前章节所在卷（没有当前章节时预选最后一卷，没有卷时预选未分卷）。侧栏新章固定追加到目标组末尾，弹窗显示这一规则而不提供位置选择；章节管理页仍可指定插入位置，移动章节保留原有内嵌表单。创建成功后关闭弹窗，侧栏打开新章节并显示其所在卷与区间。创建期间禁止重复提交或关闭，失败时保留输入并显示错误。侧栏不增加卷、章节的拖拽和删除操作。

## 前提与边界

- 章节以稳定 `chapter_id` 作为引用，界面仅展示实时计算的 `reading_number`。
- 卷顺序和卷内章节顺序共同决定阅读顺序；未分卷章节始终排在最后。
- 卷和章节的结构操作仅由前端经 App API 发起；AI 不提供卷 CRUD、插章、移动或删除章节工具。
- AI 仍可借助 `chapters/new.md` 新建正文，且可读写已有卷纲；这与前端的结构管理通道独立。
- 删除章节前必须检查 timeline、story arc、reader perspective、character relation 的章节引用；writing log 保留历史孤儿引用，不阻塞删除。

## 单一 Tab 布局

“章节管理”作为 ActivityBar 的一个独立主区域。主区域由相互联动的两部分组成，而非嵌套的卷/章节子 Tab：

1. 顶部卷轨道：按阅读顺序展示卷标签，提供新建、重命名、删除和拖拽排序。
2. 下方章节列表：按卷分组展示章节，末尾固定显示“未分卷”组；每行显示实时章节号、标题、字数和操作菜单。

选择、移动或删除卷会立即反映在下方分组和章节号中。章节拖到卷标签或“未分卷”组时，移动到对应分组末尾。

工作区占据 ActivityBar 右侧的可用宽度；进入时隐藏写作侧栏和聊天栏，但保持聊天组件挂载，以免切换页面中断正在进行的会话。离开工作区后恢复原布局。

个人中心同样只隐藏聊天栏，保持聊天组件挂载和流式会话监听。前端卷查询及后续卷操作 hook 放在 `components/volume/`，卷与章节的组合界面放在 `components/chapter-management/`。

首个前端提交只实现入口和只读展示：卷轨道、按卷分组的章节列表、加载/失败/空状态。卷与章节数据按当前小说分别查询；章节展示号采用后端返回的 `reading_number`，不在前端重新编号。AI 创建或更新章节的文件变更事件应刷新列表。卷操作和章节结构操作在后续提交开放入口。

卷轨道在列表滚动时保持可见，点击卷标签可定位并展开对应分组。超过 30 章的分组默认收起；展开后若超过 100 章，再按每 100 章的阅读编号范围分段，按需展开章节行，避免长卷把后续卷推离视野。

章节管理页按职责拆分：主 View 负责查询、分组和结构操作编排；分组组件负责展开与百章分段；章节行组件负责菜单及拖放目标；章节表单和删除反馈组件分别负责输入与确认展示。卷轨道继续独立，既有锚点语义、引用阻塞处理及缓存刷新保持一致。本次拆分并入尚未提交的章节结构操作 commit。

## 卷操作

- `PlaceVolume` 是唯一的卷结构编排入口：可创建新卷，也可移动已有卷；两者都指定目标位置。
- 位置以 `BeforeVolumeID` 表达：提供锚点时放到该卷前；为空时追加到末尾。
- 创建时 `SourceVolumeID` 为空且必须提供名称；移动时提供 `SourceVolumeID` 且不能提供名称。锚点卷必须属于当前小说。
- 因此该 API 同时覆盖末尾创建、指定位置插入和卷标签拖拽排序；前端只传本次移动动作，不传重排后的完整 ID 数组。
- 重命名：同一小说内卷名必须唯一。
- 删除卷：仅当卷内没有章节时允许；有章节时提示用户先移动或删除章节。删除时同步清理可选的卷纲文件。
- 新建卷可选择插在指定卷前或追加到末尾；重命名和删除入口放在卷轨道。位置选择复用项目的下拉框，选项明确写出“在某卷前”或“末尾”。拖动卷到另一卷标签的左半部时置于该卷前，右半部时置于该卷后；目标卷后的下一卷作为锚点，最后一卷后不传锚点。卷标签间的空隙也接收拖放并选取邻近的插入位置，轨道末尾也可追加。拖拽时显示竖向插入线，成功刷新后短暂高亮被移动卷并播放位置过渡，动效遵循系统的减少动态效果设置；拖拽只提交源卷与锚点卷 ID。
- 卷操作成功后同步刷新卷列表与章节列表，确保分组顺序和实时章节号使用同一份最新数据。卷删除的前端空卷检查只作即时提示，后端仍在执行时重新校验。

## 章节操作

- `PlaceChapter` 是唯一的章节结构编排入口：可创建新章节，也可移动已有章节；两者都指定目标卷（或未分卷组）和目标组内位置。
- 位置以 `BeforeChapterID` 表达：提供锚点时放到该章节前；为空时追加到目标组末尾。前端的“放到某章后”换算为“放到其下一章前”，最后一章后则传空锚点。
- 创建时 `SourceChapterID` 为空且必须提供标题；移动时提供 `SourceChapterID` 且不能提供标题。锚点章节必须属于目标章节组。
- 因此该 API 同时覆盖指定卷创建、卷内拖拽排序、跨卷移动、移入空卷和移回未分卷组；后端在单一事务内调整源组和目标组的排序键。
- 前端创建空正文与 AI 经 `new.md` 创建正文/大纲时，均先在外层 DB 事务中创建记录取得稳定 ID，再写对应文件；写入失败会回滚记录及排序调整。
- 删除：用户确认后调用 `DeleteChapter`；若返回阻塞引用，则展示交叉引用清单且不删除。无阻塞引用时后端在一个外层 DB 事务内删除章节记录并清理正文、大纲，文件清理失败会回滚章节记录；提交后清理对应 RAG 数据。删除后其余章节的展示编号自然连续重算。
- 每个分组提供组末新建入口；章节操作菜单提供在此章前/后插入、移动到指定分组及锚点前、删除。表单里的目标卷和插入位置复用项目的下拉框；章节位置选项明确写出“在第 X 章《标题》前”或“该分组末尾”，避免只展示章节号而无法判断动作。长卷收起时仍可向分组末尾拖入章节。
- 拖拽章节到另一章的上半部时置于目标章前，下半部时置于目标章后；放置线明确标识最终位置。“放到其后”换算为下一章的锚点 ID，目标组末尾则不传锚点。拖到分组标题或卷轨道标签时追加到该组末尾，未分卷标签也可作为放置目标。前端只提交源章节、目标卷和可选锚点章节 ID；Wails 生成的 TypeScript 可选字段省略后在 Go 侧解码为空指针，表示未分卷或组末。
- 移动成功并刷新列表后，滚动显示被移动章节，以短暂的位移和高亮反馈确认结果；跨卷及百章分段的目标章节也应可见。动画遵循系统的减少动态效果设置，避免依赖动画才能判断位置。
- 删除确认后若返回阻塞引用，界面展示引用类型、记录标签与 ID；只有 `deleted=true` 才刷新章节列表和章节总数查询。创建、移动成功后也刷新这两项查询，使侧栏和实时编号同步。
- 章节实际删除成功后关闭该章节正文或大纲的已打开编辑标签，并清除对应内容缓存，避免切回写作区后继续编辑已删除文件；确认时若标签有未保存内容，明确提示内容会丢失。阻塞删除不触碰这些标签。

## App API 边界

前端需要卷的 `PlaceVolume`、重命名、删除、查询 API，以及章节的 `PlaceChapter` 和删除 API。`PlaceVolume` 的 `source_volume_id` 与 `before_volume_id`、`PlaceChapter` 的 `source_chapter_id`、`target_volume_id` 与 `before_chapter_id` 都使用稳定 ID；可空 `target_volume_id` 明确表示未分卷组，避免使用 0 作为哨兵值。

删除 API 的失败结果应能让前端展示引用类型和引用记录，而非只给出不可删除的通用提示。

## 编辑器路径契约收尾

章节元数据同时返回 `file_path` 和 `outline_file_path`，分别指向按章节 ID 命名的正文和大纲。两个字段均由后端计算且不入库；前端只消费返回值，不从展示章节号、章节 ID 或正文路径拼出另一条路径。大纲文件可以尚未创建，路径字段仍照常返回。搜索结果、AI 文件事件及恢复的编辑标签按路径匹配当前小说的章节元数据，再取得对应的大纲路径；未取得匹配时不向猜测的路径读写。

编辑器本地缓存只存标签元数据与阅读位置，不存未保存的正文。旧缓存里的纯数字路径已无法可靠映射到章节 ID，因此通过版本号失效整个编辑器标签缓存，不清理其他 localStorage 项。章节标题中的“第几章”来自实时 `reading_number`；只有路径的场景先展示文件路径，不将 ID 误当作章节号。

实施路线：先提交后端双路径 DTO、Wails 生成绑定及前端编辑器与缓存对齐；再单独处理通用内容 API 对旧章节路径的拒绝；卷纲 `volumes/id_{id}.md` 的命名统一另成提交。卷纲尚未发布，不安排旧卷纲文件迁移。

第三个提交将 `git.VolumePath`、MCP 卷纲路径解析和 read/edit 的路径提示统一为 `volumes/id_{卷ID}.md`；删卷仍通过 `VolumePath` 清理卷纲。旧格式 `volumes/{卷ID}.md` 不再由 MCP 接受。前端卷纲读写留到后续章节列表展示改造时接入，本次不增加 App 卷纲路径校验或旧文件迁移。

通用内容 API 的第二个提交在文件读写前校验 `chapters/` 与 `outlines/` 命名空间：只接受当前小说中已有章节的扁平规范路径 `chapters/id_{id}.md`、`outlines/id_{id}.md`。旧纯数字路径、`new.md`、带卷目录的容错别名、零 ID 和非规范拼写都报错；大纲文件尚未创建时，合法读取仍返回空内容。这个校验只约束 App 的通用路径入口，MCP 工具保留自己的新建和别名解析。其他文件类型沿用现有规则。验证覆盖读取与写入，尤其要确认错误路径不会在小说仓库创建文件。

验证：章节列表、创建与移动结果均回传双路径；正文与大纲加载、保存、外部变更刷新和标签关闭使用同一组后端路径；旧版缓存不能恢复为无效标签；UI 不出现 `NaN` 章节号或 `outlines/NaN.md`。

## 验收标准

- 用户不离开“章节管理”Tab，即可完成卷和章节的全部结构操作。
- 卷重排、章节创建或移动、章节删除后，列表按正确阅读顺序展示连续编号。
- 交叉引用始终指向稳定章节 ID，不随展示编号变化。
- 有阻塞引用的章节不能被删除；有章节的卷不能被删除。
- 原有写作侧边栏切章、AI 新建章节及卷纲读写不受影响。
