# 历史升级测试的职责与维护规则

本文件适用于 `internal/migrate/upgrade/` 及其子目录。根目录 `AGENTS.md` 的工作区、修改授权、Git、日志和注释等规则继续适用。

## 核心边界

本目录验证：**每份受支持的历史安装样本，经过当前工作区代码的公开 `migrate.Run` 后，能否达到当前最新版要求，并正确保留、转换或按设计重置原有数据。**

```text
冻结的历史 ZIP → 隔离目录 → 当前代码的 migrate.Run → 对应 case 的最新版 AssertAfter + 公共检查
```

- 历史样本包含数据库、小说文件及真实 Git 历史、加密 LLM 配置，不能把范围缩减为只有 DB。
- 被测目标始终是当前代码。测试不会为了从旧版本升级而依次启动所有中间版本。
- 通用的是样本加载、运行入口和检查流程；业务结果由 case 自己断言，包括模型选择、章节引用、配置转换等。
- 不同样本可以拥有不同的数据和记录数量。统一最新版要求不意味着所有来源最终都要等于最新版 fresh seed。
- 不向历史样本补写新版 seed 来使断言通过。先区分迁移缺陷、样本准备错误和预期错误。
- 单个迁移的解析规则、歧义、事务回滚等专项边界由 `internal/migrate/vXXX/` 中的测试负责。本目录不以调用私有迁移步骤代替完整 Run。

## 历史样本的生成与来源

生成器位于仓库根目录下的 `scripts/upgrade-fixtures/`。它在当前 worktree 内的临时目录提取发布 tag 的源码，使用该版本的源码和依赖编译统一 `runner.go.tmpl`；不切换其他 worktree，也不使用当前应用模型重建历史 schema。DDL 由对应版本的 Run 执行。

### fresh

```text
v1.0.0 基础 case + 截至目标版本的 delta
→ 在内存中组合完整 Before
→ 目标 tag 的 Run 在空库建表
→ 写入 Before 的记录、配置和文件，准备小说 Git 历史
→ 关闭数据库并冻结 ZIP
```

delta 合并数据声明，不运行中间版本迁移。目标版本的 seed 必须直接符合该版本的 schema；字段、引用、配置格式和文件名变化通过替换 case 表达。

### from-v1.0.0

```text
v1.0.0 Run 建库并写入初代 Before
→ 目标 tag 的 Run 直接升级
→ 关闭数据库并冻结 ZIP
```

- 始终保留初代 case 集合和输入身份，不应用目标版本的数据 delta。
- 它表示已经被旧版 Run 迁移过的安装状态，不表示用户逐个启动了所有中间版本。
- fresh 与 from 都作为当前升级测试的输入。两者的迁移记录、遗留结构、文件历史和数据集合可能不同，不假定升级路径完全等价。
- 若以后增加逐版本升级路径，须明确新的来源语义，不能静默改变现有 origin 的含义。

## case、delta 与目录分工

```text
fixture/
├── cases/vXXX/       # 按首次引入版本组织，每个 case 独立声明
├── seeddata/         # 公共数据类型、case 类型、记录/配置/文件比较工具
├── seed_cases.go     # 显式登记 case ID 与构造函数
├── seed.go           # 版本 delta、组合、输入摘要与绑定验证
└── manifest.go       # 归档格式、哈希、来源及必要文件检查
testdata/             # 冻结的历史 ZIP 和 manifest.json
```

依赖保持为 `fixture → cases/vXXX → seeddata`，版本子包不反向依赖汇总包，不通过 `init()` 自动登记。

每个 `SeedCase` 包含：

- `ID`：稳定的输入场景身份。
- `Before`：该历史格式的输入记录、文件和 LLM 配置。一个 case 可以包含多条相关记录或多张表，例如写作明细合并、角色组与成员。
- `AssertAfter`：对该输入升级到**当前最新版**后的结果进行检查，函数返回错误供执行器报告。

维护约定：

1. 每个 case 独立声明输入与断言。registry 只登记；不要重新引入按 layout 循环生成多个历史 case 的公共模板。
2. 历史 Before 保持固定。新版本输入变化时，在新版本子包增加新 ID，通过 delta 移除旧 ID、加入新 ID；保留旧定义供旧样本使用。
3. `SeedDeltas` 按发布顺序显式列出支持的版本，包括没有变化的空 delta。每步先删除再增加；删除不存在的 ID、重复增加、未知 case 或缺少断言都应报错。
4. 删除 delta 中的选择不等于删除旧 case 文件或旧样本。
5. Before 覆盖 append-only 消息和关系时，保留历史记录及可见性标志，遵循生产数据语义。

## AssertAfter 只面向最新版

- `cases/v100` 表示输入首次引入于 v1.0.0，其 AssertAfter 仍然随当前最新版维护，不是冻结的 v1.0.0 验收标准。
- 不保存按目标版本分叉的 After；当前迁移语义变化时，更新所有受影响历史 case 的断言。
- 预期由测试明确声明，不能运行被测 Run 后把实际结果保存为正确预期，也不能复用生产转换函数计算正确答案。
- 字段发生变化的场景应明确写出目标字段和值，不借用另一个版本 case 的 Before 构造预期。原样保留的场景可以明确断言与自己的 Before 一致。
- 一个 AssertAfter 可以检查多条记录、多个字段、文件、配置等；不局限于一条断言。比较工具放在 seeddata，业务预期留在所属 case。
- 普通业务场景优先通过 case 和 delta 表达，避免另建测试临时修改旧库、重复维护一套业务后校验。

**生成器集成测试不能在仅运行历史 tag 的 Run 后调用当前 AssertAfter。** 它应在写入后核对该版本 Before，验证输入身份、完整性及运行稳定性。from 的初代输入在历史升级之前核对；升级后不再要求旧列原样存在。最新版业务后校验由本目录在当前 Run 执行后负责。

## 当前测试流程

`TestHistoricalDirectUpgrades` 从 manifest 选择历史样本，逐份执行：

1. 验证归档和输入绑定，将 ZIP 解压到独立临时目录，记录原始数据、文件与配置。
2. 用独立 worker 进程调用当前 `migrate.Run`，隔离 HOME、数据目录、配置单例和 Git 环境。
3. `assertContract` 解析归档实际使用的 case，逐个调用当前 AssertAfter；检查无预期数据的表、迁移完成状态、SQLite 完整性和小说 Git 历史。
4. 对照当前 Run 创建的新库检查目标列和索引，并检查明确退役的旧字段。需要备份时，检查备份保存了原始数据、文件和 Git HEAD。
5. 重启再次 Run，比较数据库、文件、配置和 Git HEAD，确认没有额外改写。
6. 删除隔离副本的迁移状态后再次 Run，检查业务结果和资源仍然稳定。
7. 通过当前 Store/API 做读写探测，确认升级后的数据库可供当前代码正常使用。

基础设施场景可以单独选择适当的历史样本，模拟备份失败、文件阻塞、未提交正文和恢复。故障只注入隔离副本，不修改冻结 ZIP 或生产迁移实现来制造测试条件。

`case_assertions_test.go` 先确认正常升级结果通过，再破坏隔离副本的数据、文件或配置，要求对应 case 拒绝错误结果。这验证断言的检错能力，不等于已经覆盖所有真实迁移缺陷。

## 归档与输入的约束

- manifest 记录 tag、源码 commit、origin、ZIP SHA256、case IDs、Before 输入摘要和小说 Git HEAD；使用时验证其一致性。
- 输入摘要覆盖实际选择的 case IDs 与组合后的 Before，不包含 AssertAfter。
- 只修改最新版断言或重组代码且 Before 不变，不需要重建 ZIP。Before 或选择集合变化时，必须检查受影响样本并通过生成器重建，更新 manifest。
- 不能手改哈希来掩盖不一致。普通生成不覆盖已冻结归档；显式重建仍校验原归档哈希和来源 commit。
- 关闭数据库后才能冻结，不能把活跃 WAL/SHM 当作完整归档。测试不使用真实用户数据或凭据。
- 生成器会在临时小说仓库中执行 Git 初始化、配置、暂存和提交。这与项目仓库的 Git 写操作不同，执行仍遵守根目录的授权规则；运行生成器不授权暂存或提交项目改动。

## 当前限制

- 同一份输入中，一张表只能由一个 case 提供记录，公共行比较按整表核对。需要多个同表 case 时，应先明确记录归属、局部检查和整表完整性规则，不能只删除冲突检测。
- `AssertRows` 当前忽略 created_at/updated_at，并从首条预期记录提取比较列。现有 case 同表记录的字段集合一致；后续记录的额外字段可能漏查，这是当前实现缺口，不应视作允许忽略已声明字段的规则。
- 当前结构参考由同一个 Run 新建空库得到，主要验证升级与新建的一致性；它不能独立证明最新版结构定义本身没有遗漏。
- 输入摘要验证声明绑定，不代替数据库内容校验。生成器集成测试目前核对代表性版本的 Before，不是全部 tag 的通用 AssertBefore。
- 检出范围取决于实际 case 和断言；空表、未声明字段和未准备的历史组合不能算作已有数据覆盖。

## 执行与维护

所有命令从仓库根目录执行。黑盒测试需要 cgo、SQLite 系统依赖和真实 Git；归档生成仅支持 Linux，已有归档的消费测试可跨平台。

```sh
go run ./scripts/upgrade-fixtures -check
go test -tags=upgrade -count=1 -timeout=15m ./internal/migrate/upgrade/... ./scripts/upgrade-fixtures/...
```

- 稳定发布目标通过检查命令的 `-target` 和测试的 `UPGRADE_TARGET` 保持一致，只选择严格低于目标的历史版本；开发构建不指定目标时检查所有支持的发布 tag。
- `GOINK_UPGRADE_REPORT_DIR` 指定 worker 日志和失败样本的保存目录；`GOINK_UPGRADE_TARGET_COMMIT` 用于诊断日志标识，不控制实际执行的代码版本。
- 新增场景时：独立声明 case → 登记 ID → 增加或调整版本 delta → 检查历史输入变化 → 按已授权范围重建受影响归档 → 验证当前 Run 和断言。仅增加版本而无输入变化也应声明空 delta。
- 修改比较工具或迁移后校验时，按风险选择能揭示遗漏、错误转换或多余记录的故障场景，确认正确输入通过、错误结果失败。
- 文档变更不要求重跑全部测试。代码变更按影响范围验证，完成后遵循根目录规则等待 review，不自动暂存、提交或推送。
